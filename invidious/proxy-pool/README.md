# Ротация исходящего прокси для invidious-companion

Автоматическая смена исходящего IP, когда YouTube/BotGuard перестаёт отдавать
companion рабочую сессию.

> ## ⚠ Пул выключен и включать его «просто так» нельзя
>
> Ссылки googlevideo **привязаны к IP того, кто их запросил**: в URL есть
> параметр `ip=`, и он входит в подписанный `sparams`. Companion за прокси
> выдаёт ссылку, привязанную к адресу прокси, а байты качает бэкенд — со
> своего адреса (`ytdlp.py:1682`, `1448`). Результат — `403 Forbidden` на
> каждом стриме при исправном резолве.
>
> Проверено на практике 2026-08-17: с включённым пулом резолв работал, а
> воспроизведение падало с 403 на `rr5---sn-*.googlevideo.com` (ссылка была
> привязана к выходу EDIS GmbH / AS57169).
>
> Поэтому: **не включайте оверлей и не enable'те таймер**, пока в бэкенде не
> сделано проксирование самого стриминга (нужно в трёх местах: основной поток
> `ytdlp.py:1682`, прогрев `ytdlp.py:1448`, архивация
> `external_archive.py:505,658`) плюс сброс `ytdlp:resolve:v2:*` при каждой
> ротации — иначе кэшированные ссылки прежнего выхода продолжат отдавать 403.
> И учтите цену: через прокси пойдёт весь звук, ~5 МБ на трек.
>
> Пул имеет смысл включать, только если companion **не может** выпустить
> PO-token с адреса сервера. Проверять это надо каждый раз заново — блокировка
> снимается сама (в тот раз оказалось, что достаточно снести кэш сессии):
>
> ```bash
> docker compose -f docker-compose.prod.yml rm -sf invidious-companion
> docker volume ls -q --filter name=companioncache | xargs -r docker volume rm
> docker compose -f docker-compose.prod.yml up -d && sleep 60
> curl -s http://127.0.0.1:3050/api/v1/videos/dQw4w9WgXcQ | grep -c '"type":"audio'
> ```
>
> Ненулевой ответ — прокси не нужен, оставьте стек без второго `-f`.
> При любом переключении пула (включили или выключили) сбрасывайте кэш резолва:
> в нём лежат ссылки, привязанные к прежнему адресу.
>
> ```bash
> docker exec music_redis redis-cli --scan --pattern 'ytdlp:resolve:v2:*' \
>   | xargs -r -n100 docker exec -i music_redis redis-cli del
> ```

| Файл | Роль |
|---|---|
| `proxies.list` (из `.example`) | пул: `IP:PORT:USER:PASS[|лимит]`, у каждого свои креды и лимит |
| `active.env` | активный выход; **генерируется** `rotate.sh`, читается compose |
| `../docker-compose.proxy.yml` | подключает `active.env` к companion |
| `rotate.sh` | проверка, выбор выхода, перевыпуск сессии |
| `systemd/` | запуск проверки раз в 5 минут |

## Как это устроено

Активный выход всегда **один**: PO-token и `visitor_data` привязаны к адресу,
с которого выпускались, и запрос с другого IP YouTube встречает тем же
non-200, что и блокировку. Поэтому балансировки здесь нет вовсе — есть
назначенный выход и смена назначения.

У прокси может быть месячный лимит трафика: добавьте к строке `|100GB` (также
поддерживаются `B`, `KB`, `MB`, `TB`). Счётчик фактически переданных
googlevideo-байтов хранится в Redis по UTC-месяцам. При исчерпании лимита прокси
сразу исключается из пула; при ротации выбирается проверенный выход с наибольшим
остатком. Строки без суффикса `|...` остаются безлимитными. `--status` показывает
текущий расход и лимит.

Раз в 5 минут `rotate.sh` спрашивает Invidious, отдаёт ли он аудио-форматы (то
же, что проверяет бэкенд в `_resolve_via_invidious`,
`backend/app/routers/ytdlp.py:662`). Companion при неудачном выпуске токена не
падает и порт не закрывает, поэтому docker healthcheck такую деградацию не
видит.

Два промаха подряд → скрипт выясняет **причину**, прежде чем что-то менять:

- watch-страница через текущий прокси отдаёт `playabilityStatus: OK` → адрес не
  в блоке, виновата сессия. Перевыпускаем её на том же прокси, адрес из пула не
  тратим.
- страница не отдаёт → YouTube больше не обслуживает этот IP. Ищем в списке
  рабочий прокси с наибольшим остатком лимита и только тогда переключаемся:
  старый уходит «отдыхать» на час, новый пишется в `active.env`, companion
  пересоздаётся со сносом кэша `youtube.js`.

Кандидат проверяется **до** переключения: иначе смена выхода могла бы оставить
companion вообще без работающего egress до следующего срабатывания таймера.

Если рабочего кандидата в пуле нет, включается **direct-режим**: `active.env`
перезаписывается с закомментированными прокси-переменными, companion
пересоздаётся уже без оверлея `docker-compose.proxy.yml` и работает с адреса
самого VPS, бэкенд качает googlevideo напрямую. Пока прямой выход отдаёт
аудио, скрипт его не трогает; при его деградации сначала ищется оживший
прокси (нашли — проксирование возвращается), затем перевыпускается сессия
прямого выхода. Вернуться в пул вручную: `rotate.sh --activate N`. Признак
режима — файл `/var/lib/invidious-proxy-rotate/direct`, текущее состояние
показывает `--status`.

Между вмешательствами держится `MIN_INTERVAL` (10 мин). Без него цикл
«переключение → минт → отказ» сжёг бы весь пул за минуты в случае, когда
причина вообще не в IP — по смыслу это тот же бэкофф, что `_BOT_CHECK_TTL` у
бэкенда для yt-dlp.

## Требования к прокси

**HTTP-прокси с CONNECT, не SOCKS5.** Companion читает переменную `PROXY`
(собственная настройка `networking.proxy`, см. `config.example.toml` в его
репозитории) и передаёт её в `Deno.createHttpClient`. Проверить адрес до
внесения в список:

```bash
curl -s --max-time 15 -x http://USER:PASS@IP:PORT https://api.ipify.org
```

Ответ должен быть IP самого прокси.

**Пароль с любыми символами допустим** — `rotate.sh` кодирует логин и пароль
перед сборкой URL (`@`, `:`, `/` в пароле не разъедутся). IPv6-адреса не
поддержаны: двоеточия в них неотличимы от разделителей формата.

**Residential/mobile лучше датацентровых.** BotGuard блокирует hosting-ASN
охотнее; проверить, чем является адрес, можно так:

```bash
curl -s "http://ip-api.com/json/IP?fields=isp,as,mobile,hosting"
```

`hosting: true` не приговор — блокируют не диапазон целиком, а адреса по
поведению, — но если проверку не проходит ни один прокси в пуле, дело почти
наверняка в этом, а не в скрипте.

## Установка

Только после того, как выполнено условие из блока выше (проксирование
стриминга в бэкенде), иначе получите 403 на воспроизведении.

```bash
cd /opt/music-service/invidious
cp proxy-pool/proxies.list.example proxy-pool/proxies.list   # вписать свои прокси
chmod 600 proxy-pool/proxies.list                            # в файле пароли
chmod +x proxy-pool/rotate.sh

# назначить стартовый выход (создаёт active.env, без него compose не стартует)
COMPOSE_DIR=$PWD proxy-pool/rotate.sh --activate 1

docker compose -f docker-compose.prod.yml -f docker-compose.proxy.yml up -d

install -m644 proxy-pool/systemd/invidious-proxy-rotate.{service,timer} /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now invidious-proxy-rotate.timer
```

Оба `-f` нужны при **каждом** последующем `up`/`restart`: без второго файла
companion пересоздастся без прокси-переменных и уйдёт в сеть напрямую.

Обратная сторона того же: `rotate.sh` всегда вызывает compose с **двумя** `-f`.
Если таймер оставить включённым при выключенном пуле, первая же деградация
Invidious вернёт оверлей обратно — вместе с 403 на стриминге. Выключается так:

```bash
systemctl disable --now invidious-proxy-rotate.timer
```

## Эксплуатация

```bash
proxy-pool/rotate.sh --status         # активный выход, промахи, кто отдыхает
proxy-pool/rotate.sh --activate 2     # назначить выход №2 вручную
journalctl -u invidious-proxy-rotate -n 50   # что делала автоматика
```

`--activate` проверяет прокси и предупреждает, если YouTube его не
обслуживает, но назначает всё равно: раз выход указан руками, решение за
оператором. Сессия при этом перевыпускается всегда.

## Проверки после установки

1. Конфиг compose валиден и `active.env` подхватился:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.proxy.yml config \
  | grep -A2 PROXY
```

2. **Обязательная проверка.** Companion применяет прокси только через свою
   переменную `PROXY` (в `active.env` её пишет `rotate.sh`); в логе при старте
   она должна попасть в конфиг:

```bash
docker logs invidious-invidious-companion-1 2>&1 | grep -m1 'Loaded Configuration'
```

   В `"networking": { "proxy": ... }` должен быть адрес активного прокси.
   Раньше схема держалась на допущении, что Deno-fetch уважает стандартные
   `HTTPS_PROXY`/`HTTP_PROXY` — оно не подтвердилось (companion передаёт в
   fetch собственный клиент с прокси только из `PROXY`), из-за чего трафик
   мог молча ходить с адреса VPS при любой ротации.

3. Резолв реально работает (то же, что дёргает бэкенд):

```bash
curl -s http://127.0.0.1:3050/api/v1/videos/dQw4w9WgXcQ \
  | grep -c '"type":"audio'
```

Ноль — сессия ещё не выпущена (после пересоздания это занимает до минуты) или
выход в блоке.

4. Прогон автоматики без права вмешательства — видно только результат
   проверки:

```bash
COMPOSE_DIR=$PWD FAIL_THRESHOLD=99 proxy-pool/rotate.sh
```

## Что стоит знать заранее

**Переключение занимает до 5 минут** (интервал таймера) плюс время выпуска
новой сессии. Мгновенного failover здесь нет и быть не может: смена выхода без
перевыпуска токена бесполезна, а перевыпуск — это пересоздание контейнера.
Пока Invidious не отвечает, бэкенд резолвит через yt-dlp, то есть медленнее,
но играет.

**yt-dlp этот пул не затрагивает.** Он живёт в контейнере `backend` другого
стека и ходит к YouTube с адреса сервера. Bot-check на его стороне лечится
своим бэкоффом (`_BOT_CHECK_TTL` в `ytdlp.py`), а не ротацией здесь.

**Деградация Invidious стоит бэкенду 0.6 с на резолв.** Состояние инстанса
нигде не запоминается: до вмешательства каждый трек платит `_HEDGE_DELAY`,
прежде чем стартует yt-dlp (`ytdlp.py:969`). Circuit breaker по образцу
`bot_check_active()` не реализован — это отдельная правка в бэкенде.

**Проверка прокси — не проверка BotGuard.** `playabilityStatus: OK` говорит,
что адрес не в блоке у web-клиента; воспроизвести сам челлендж выпуска
PO-token скрипт не может. Поэтому возможен случай, когда кандидат проверку
прошёл, а сессия на нём всё равно не выпустилась: тогда следующий цикл
отправит и его отдыхать и возьмёт следующего.

**Секреты.** `proxies.list` и `active.env` в `.gitignore`; `active.env`
генерируется с режимом 0600. Пароли в журнал не попадают — логируется только
`ip:port`.

## Если переменная PROXY не работает

Путь через `PROXY` — штатный для companion (`Deno.createHttpClient`), но если
в вашей версии образа он вдруг не применился (в логе `"networking": {"proxy":
null}` при заполненном `active.env`), нужен прозрачный перехват:
контейнер-шлюз (redsocks/gluetun-подобный) и `network_mode: "service:<шлюз>"`
у companion — весь его egress уйдёт через шлюз независимо от поддержки прокси
в рантайме. Логика ротации при этом не меняется: «проверить → сменить выход →
перевыпустить сессию» не зависит от способа доставки трафика, меняется только
то, что `rotate.sh` переписывает конфиг шлюза вместо `active.env`.
