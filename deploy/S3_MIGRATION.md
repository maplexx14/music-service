# Перенос S3 через mc mirror

Источник: `src/bms`. Назначение: `dst/bol`. Оба аккаунта используют
`https://s3.buckets.ru/`, регион `ru-1`, с разными ключами доступа.
Копирование выполняется на действующем сервере приложения. Переключение S3
выполняется отдельным этапом после финальной сверки при остановленной записи.
Новые параметры сохранены в игнорируемом `.env.s3-target.local`;
в репозитории есть только `.env.s3-target.example`.

## Настройка MinIO Client

На сервере установлен официальный `mc RELEASE.2025-08-13T08-35-41Z`.
Бинарник скачан из GitHub Releases MinIO и проверен по опубликованному SHA-256.
Для миграции используется отдельная конфигурация с правами доступа только владельцу:

```bash
umask 077
mkdir -p "$MC_CONFIG_DIR"
mc --config-dir "$MC_CONFIG_DIR" alias set src https://s3.buckets.ru --api S3v4 --path on
mc --config-dir "$MC_CONFIG_DIR" alias set dst https://s3.buckets.ru --api S3v4 --path on
```

`MC_CONFIG_DIR` — абсолютный путь к отдельному каталогу конфигурации.
Каждая команда запросит access key и secret key своего аккаунта.
Не записывайте ключи в документацию, git или общий журнал.

Объекты источника зашифрованы SSE-C. На назначении используется тот же
32-байтовый ключ шифрования. Для `--enc-c` переменная `SSE_C_HEX` должна
содержать его в виде 64 шестнадцатеричных символов. Исходный `S3_SSE_C_KEY`
из конфигурации приложения хранится в base64; его нужно декодировать и
преобразовать в hex. Ключи доступа S3 и ключ SSE-C — разные значения.

## Прямое копирование: проверенная настройка и ограничение

```bash
mc --config-dir "$MC_CONFIG_DIR" mirror \
  --json --overwrite --md5 --disable-multipart --retry --skip-errors --summary \
  --max-workers 32 \
  --enc-c "src/bms=$SSE_C_HEX" \
  --enc-c "dst/bol=$SSE_C_HEX" \
  src/bms dst/bol
```

Команда переносит все текущие объекты с исходными путями, включая `music/`
и `covers/`. Старый бакет сохраняется. Флаги `--remove` и `--preserve`
не используются: удаления и перенос настроек бакета не входят в эту операцию.

Для этого провайдера используются проверенные настройки:

- `--md5`: без него прямое копирование отдельного MP3 завершалось
  `SignatureDoesNotMatch`; с ним тот же файл передался успешно.
  Для удалённого источника `mc` буферизует объект перед отправкой и передаёт Content-MD5.
- `--disable-multipart`: загрузка выполняется одним PUT, обходя наблюдавшиеся
  ошибки `InvalidPart` у провайдера. Все объекты текущего архива меньше 55 МБ.
- `--overwrite`: разрешает обновление существующих копий. При повторном запуске
  `mc` может заново передать объекты, которые считает отличающимися.
- `--max-workers 32`: ограничивает параллельность и память на буферизацию.

Эта команда успешно передаёт часть файлов, но прямой поток для FLAC размером
46 866 500 байт завершился ошибкой `ContentLength=46866500 with Body length 10485760`.
Тот же файл полностью скачался и загрузился через локальный файл.
Поэтому текущий перенос выполняется через временный каталог двумя командами
`mc mirror`: S3 → локальные файлы, затем локальные файлы → новый S3.

## Текущий перенос партиями

`mc_staged_supervisor.py` в закрытом каталоге задачи управляет только запуском
`mc` и сверкой списков. Каждая партия ограничена 2 ГиБ. Два временных каталога
используются по очереди: пока готовая партия загружается в новый S3,
следующая скачивается. Общий объём временных файлов — не более 4 ГиБ. Размер
следующей партии уменьшается по свободному месту, чтобы оставить 2 ГиБ резерва;
при нехватке места предварительное скачивание пропускается.
На первом проходе маски `--exclude` выбирают конкретную партию из исходного
бакета. Перед вторым проходом проверяется наличие и размер каждого локального
файла; для загрузки используются `--md5`, `--disable-multipart` и SSE-C нового
аккаунта. После загрузки список `bol` проверяется по ключам и размерам. Удаляются
только подтверждённые локальные копии; недогруженные файлы сохраняются для повтора.
Загрузка запускается отдельно для каждого исходного каталога, например
`mirror-stage/music/external/ytmusic` → `dst/bol/music/external/ytmusic`.
Это сохраняет пути объектов и сокращает число страниц S3-списка, на которых
провайдер периодически возвращает `SignatureDoesNotMatch`.
При сверке учитываются ошибки из stdout и stderr. Пустой или укороченный список
назначения относительно уже подтверждённого числа объектов отклоняется;
одна попытка чтения списка ограничена 75 секундами и повторяется до пяти раз.
В текущем переносе используется обычный `mc mirror` по каталогам. Для чтения
списков S3 пути бакетов заканчиваются `/`, чтобы `mc` возвращал ключи относительно
бакета. Если непустые списки источника и назначения полностью расходятся по ключам,
проход останавливается до очистки временных файлов, а образцы путей сохраняются
для диагностики в `mc-key-mismatch.json`.
Полная сверка актуальных
списков обоих бакетов выполняется после каждых четырёх партий и перед завершением;
ошибки промежуточных загрузок попадают в следующий проход.

Не запускайте зеркалирование всего бакета на локальный диск: свободного места
на сервере недостаточно для всего архива. Supervisor сохраняет резерв диска,
повторяет недокопированные партии и помечает операцию завершённой только после
сверки всех исходных путей и размеров и проверки SHA-256 выбранных треков и
обложек. Повторные ошибки без прогресса дают статус `failed`.

Если остаётся не более 128 объектов или партии повторно не дают прогресса,
обрывающиеся ответы дочитываются через
`mc cat --offset`. Каждый ответ диапазона проверяется по смещению, полному размеру
и неизменному ETag. Данные пишет сам `mc` во временный файл; готовый файл загружается
через `mc mirror`. SHA-256 этих файлов сохраняется для последующей проверки.
Выборочная проверка содержимого также допускает дочитывание через диапазоны.
Проверка SHA-256 выполняется в восемь потоков; каждый выбранный файл полностью
читается через `mc` из обоих бакетов, а успешно проверенные образцы отражаются
в текущем статусе по мере завершения.

Для HTTPS-запросов `mc` используется локальный CONNECT-туннель с таймаутом
45 секунд без обмена данными. Он передаёт TLS без расшифровки и слушает только
loopback; доступ разрешён только к `s3.buckets.ru:443`. Это обходит отсутствие
таймаута чтения в прямом HTTPS-dialer используемой версии `mc`.

Скачивание прерывается, если за 45 секунд объём готовых локальных файлов не вырос
на 8 МиБ, либо за 90 секунд не появился ни один готовый файл;
один проход скачивания ограничен пятью минутами, загрузки — тремя минутами.
Полные файлы загружаются, а оставшиеся объекты снова выбираются по сверке бакетов.

При локальном промежуточном хранении исходные S3-метаданные автоматически не
сохраняются: `mc` определяет Content-Type при загрузке локального файла.
Пути, содержимое и ключ SSE-C сохраняются. История версий, политики бакета и
маркеры удаления не переносятся.

Для передачи через локальные файлы заданы `--max-workers 64`,
`GOMAXPROCS=64` и `GOMEMLIMIT=2GiB`;
регион явно задан через `MC_REGION=ru-1`.

На сервере процесс запущен отдельным supervisor и продолжает работать при
разрыве SSH. Закрытые конфигурация, статус и журналы находятся в:

```text
/root/music-service/logs/s3-migration-20261104-2332b0b1891c/
```

Из локального проекта текущий статус и независимая сверка доступны через:

```powershell
& 'logs/tooling/venv/Scripts/python.exe' 'logs/s3-migration-2026-11-04/remote_migration.py' status
& 'logs/tooling/venv/Scripts/python.exe' 'logs/s3-migration-2026-11-04/remote_migration.py' mc-inventory
```

Это SSH-обёртка для запуска и наблюдения за `mc`; файлы передаёт сам `mc mirror`.
Для повторного запуска после ошибки используется действие `mc-stage-start`;
оно заново сверяет бакеты, догружает сохранившиеся полные временные файлы
и выбирает оставшиеся объекты.

## Проверка и повторный проход

Код завершения сам по себе недостаточен: ранее `mc` вернул 0 после ошибки
сравнения списков без передачи данных. Проверьте ошибки в журнале и независимо
сравните рекурсивные списки обоих бакетов: наличие каждого исходного ключа
и совпадение его размера. Итог `mc-inventory` должен показать
`missing_objects: 0` и `size_mismatches: 0`.

Сверка списков не подтверждает полную побайтовую идентичность архива.
Для проверки содержимого прочитайте выбранные треки и обложки через
`mc cat --enc-c` и сравните SHA-256. При чтении одного бакета указывайте
только его `--enc-c`.

Во время копирования приложение может продолжать писать в `bms`, поэтому новые файлы могут появиться
после прохода. Повторите `mc mirror` и сверку для актуального состояния.
Копирование текущих объектов не переносит историю версий и маркеры удаления.

## Переключение приложения — отдельный шаг

Во время копирования настройки работающих сервисов не меняются.
Перед переключением требуется остановить записи в старый бакет,
сделать финальный проход и проверить его результат.

На действующем сервере Compose получает конфигурацию из `/root/music-service/.env`
через `--env-file`. Изменять нужно этот активный файл.

Сохраните старые S3-параметры в закрытый локальный файл, перенесите новые
`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`,
`S3_SSE_C_KEY` и `S3_SINGLE_PUT_MAX_MB` в активный env-файл, затем пересоздайте
`backend` и `flow-warmer` и перезагрузите nginx. Проверьте чтение старого трека
без попадания в дисковый кэш, перемотку, обложку и новую загрузку в `bol`.
Логические пути `minio://music/<key>` в БД сохраняются.

Для отката восстановите старые параметры и пересоздайте сервисы.
Если новый бакет уже принимал записи, сначала согласуйте данные обоих бакетов.
